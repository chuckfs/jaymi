Database

**Status: Current Implementation** (SQLite schema) · **Target:** full knowledge graph productization

The database is Jaymi’s persistent knowledge store.

Its purpose is not simply to store data.

Its purpose is to organize relationships between conversations, memories, projects, files, providers, and user knowledge in a way that allows Jaymi to retrieve meaningful context quickly and accurately.

The database should represent knowledge—not just records.

### Current schema (shipped tables / stores)

* system events / settings
* discovered inventory items
* normalized content
* embeddings queue / vectors
* memories
* conversations (messages, attachments, references)
* projects

### Target (documented; no unused Rust stubs)

Conceptual entity / relationship model below is the product target. Unused
placeholder graph types (`entities` / `relationships` / `events` modules) were
removed — implement against real schema tables when productizing the graph.

* Rich entity / relationship knowledge graph APIs
* First-class artifact / tool / provider tables beyond identity metadata
* Full export of all entity types

⸻

Philosophy

Jaymi should think in relationships.

Not tables.

Everything stored by Jaymi should be discoverable, searchable, and connected.

The database exists to answer questions such as:

* What is this?
* How is it related?
* Where did it come from?
* Why is it important?
* When was it last used?

⸻

Core Concepts

Every piece of information belongs to an entity.

Entities may be connected through relationships.

Together they form Jaymi’s knowledge graph.

⸻

Primary Entities

Jaymi stores information using a small number of core entities.

User

Represents the owner of the system.

Contains:

* Preferences
* Settings
* Policies
* Personal Memory

⸻

Conversation

Represents a conversation between the user and Jaymi.

Contains:

* Messages
* Attachments
* Planner history
* Tool executions
* Context snapshots

Conversations may belong to projects.

⸻

Project

Represents a workspace.

Contains:

* Files
* Conversations
* Memories
* Tasks
* Artifacts
* Configuration

Projects remain portable.

⸻

Memory

Represents intentionally retained knowledge.

Contains:

* Summary
* Content
* Embedding
* Metadata
* Relationships

Memories are searchable and editable.

⸻

File

Represents any indexed file.

Examples:

* Documents
* Images
* Source Code
* PDFs
* Notes

Files are indexed rather than duplicated whenever possible.

⸻

Artifact

Represents content generated by Jaymi.

Examples:

* Images
* Reports
* Code patches
* Documents
* Diagrams

Artifacts remain attached to conversations and projects.

⸻

Task

Represents work in progress.

Tasks may belong to:

* Conversations
* Projects
* Memories

Tasks are optional.

⸻

Provider

Represents an installed provider.

Contains:

* Metadata
* Configuration
* Supported capabilities
* Health status

⸻

Tool

Represents an executable operation.

Contains:

* Metadata
* Provider
* Capability
* Execution statistics

⸻

⸻

Search Indexes

The database should support multiple search strategies.

Examples:

* Keyword search
* Semantic search
* Metadata search
* Relationship traversal
* Recent activity
* Project-local search
* Global search

The Planner decides which strategy is appropriate.

⸻

Embeddings

Embeddings are stored separately from raw content.

Embeddings may exist for:

* Memories
* Conversations
* Documents
* Files
* Images
* Tasks
* Artifacts

Embeddings should always reference their original source.

The original data remains authoritative.

⸻

Metadata

Every entity should expose common metadata.

Examples:

* Unique ID
* Creation date
* Last modified
* Source
* Tags
* Owner
* Relationships
* Importance
* Version

Consistent metadata enables consistent retrieval.

⸻

Event History

Jaymi should maintain an internal event log.

Examples:

* Conversation created
* Memory promoted
* Provider installed
* Project opened
* Tool executed
* Permission granted

The event log enables auditing, debugging, and future automation.

⸻

Caching

Caches improve performance.

Caches do not represent truth.

Cached data should always be replaceable.

If a cache is lost, Jaymi should be able to rebuild it.

⸻

Local First

The database should remain local by default.

Cloud synchronization, if implemented, should be optional.

Every record should remain exportable.

Users own their data.

⸻

Portability

Users should always be able to export:

* Projects
* Memories
* Conversations
* Artifacts
* Tasks

Jaymi should never trap user knowledge inside its database.

⸻

Design Principles

The database should always be:

* Local
* Portable
* Searchable
* Explainable
* Extensible
* Relationship-driven
* Recoverable

The database stores knowledge.

The Planner creates intelligence.

⸻

Long-Term Vision

As Jaymi grows, millions of entities may exist.

The architecture should scale naturally because information is connected through relationships rather than isolated tables.

The user should never think about the database.

They simply ask a question.

Jaymi discovers the relevant knowledge, assembles context, and responds naturally.

The database remains invisible while making everything else possible.
